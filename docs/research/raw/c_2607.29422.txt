### **2. How This Work Fits into the Broader Research Landscape**

Software vulnerabilities represent a persistent and significant threat to modern software systems, frequently leading to severe security incidents. Manual patching of these flaws is a time-consuming and expertise-intensive process, with prior studies indicating a median time of over 70 days from vulnerability disclosure to patch deployment. This motivates research into automated vulnerability repair.

The field of automated vulnerability repair has evolved through several stages:
*   **Early learning-based approaches:** These methods, such as VRepair and VulRepair, typically fine-tuned smaller language models (e.g., CodeT5) on individual vulnerable functions. They framed the task as sequence-to-sequence learning. However, they were limited by strict input-length windows, treated code as flat text, and primarily focused on single-function scope, making them ineffective for vulnerabilities spanning multiple files or requiring structural awareness.
*   **LLM-based approaches:** More recent methods leveraged larger language models (LLMs) with extended context windows, treating vulnerability repair as a zero- or few-shot generation task. Examples include iterative dialogue with ChatGPT or fine-tuning billion-parameter models like CodeLlama and StarCoder using parameter-efficient techniques. While these approaches showed improvements and could incorporate reasoning, most were still restricted to function-level repair within a single file, lacking cross-file or cross-directory reasoning capabilities essential for many complex vulnerabilities.
*   **Agentic repair approaches:** The current state-of-the-art for general program repair involves agentic systems. These systems orchestrate multiple LLM-driven subagents that can autonomously read, edit, and cross-reference files across an entire repository, execute tests, and iteratively refine patches based on execution feedback. Frameworks like RepairAgent, AutoCodeRover, and SWE-Agent were primarily designed for general bug repair, demonstrating capabilities for repository-level reasoning.

Despite the advancements in agentic repair for general bugs, their application to security vulnerability repair presents specific challenges. Security vulnerabilities often arise from subtle low-level interactions, cross-file data flows, and fragile historical code patterns, which require a richer and more structured program context than general software bugs. Existing general-purpose agentic systems typically rely on file navigation, code retrieval, and compiler/test feedback, but do not explicitly engineer the security-relevant program context that human security engineers routinely assemble. This gap in program context engineering for agentic vulnerability repair is the specific problem that the presented work aims to address. The paper identifies three critical facets of contextâcode-structure, runtime-execution, and commit-historyâthat are well-studied in software engineering but have not been jointly engineered into a unified repair context for agentic systems.

### **3. Key Objectives and Motivation**

The primary motivation for this research stems from the persistent and substantial challenge of addressing software vulnerabilities. Manually patching these flaws is a time-consuming and expertise-intensive task, leading to prolonged vulnerability exposure windows and significant security risks. While automated program repair has progressed, existing approaches, including recent agentic AI methods, exhibit limitations when confronted with the unique demands of security vulnerability repair.

The paper identifies specific deficiencies in current agentic repair approaches, which primarily focus on general bug repair and do not adequately capture the rich, security-specific program context that human security engineers typically leverage. These deficiencies lead to three critical gaps:

1.  **Limited Code-Structure Context:** Vulnerabilities often originate from subtle structural issues, such as cross-file data flows, intricate memory operation patterns, and compiler-level data layouts (e.g., packed bitfields). Existing agentic systems, by treating code largely as flat text or lacking deep semantic analysis, struggle to detect or understand these structural complexities. For example, a use-of-uninitialized-value vulnerability might stem from a packed bitfield struct where writing to one field inadvertently reads random bytes from another sharing the same memory location, a problem requiring deep structural insight.
2.  **Limited Runtime-Execution Context:** Security vulnerabilities frequently manifest through specific runtime behaviors, such as crash semantics, precise memory access violations, and the origins of uninitialized or corrupted memory. Current agentic approaches often rely on general test feedback but lack mechanisms for in-depth dynamic instrumentation and runtime origin tracking that can connect allocation sites across file boundaries or pinpoint the exact cause of a crash. An unbounded buffer read, for instance, might be triggered by uninitialized memory originating from a `malloc()` call in a completely different file, requiring detailed runtime tracing to diagnose.
3.  **Limited Commit-History Context:** Understanding how fragile code patterns were introduced, modified, or evolved over time is crucial for diagnosing and correctly repairing certain vulnerabilities. Historical context can reveal the evolutionary root cause of vulnerable code structures and the intent behind prior changes that inadvertently created security flaws. Existing agentic systems generally do not incorporate version control history mining or historical origin context into their reasoning process, making it difficult to trace the evolution of vulnerabilities.

Given these limitations, the key objective of this work is to address the challenge of **program context engineering** for agentic vulnerability repair. Specifically, the authors aim to:

*   **Operationalize multi-faceted program context engineering:** Design and implement an agentic vulnerability repair framework that explicitly integrates and leverages code-structure, runtime-execution, and commit-history contexts.
*   **Improve vulnerability repair accuracy:** Develop a system that can generate correct and safe patches for real-world security vulnerabilities, significantly outperforming existing agentic and LLM-based approaches by providing a more comprehensive understanding of the underlying security flaws.
*   **Demonstrate the complementarity of context facets:** Investigate through ablation studies whether these distinct context types are mutually beneficial and contribute collectively to the repair process.
*   **Analyze the impact of architectural components:** Evaluate the contributions of multi-agent scaffolding and the capacity of base LLMs to the overall effectiveness of the framework.

By achieving these objectives, the research seeks to bridge the gap between how security engineers diagnose complex vulnerabilities in practice and how current agentic AI approaches assemble program understanding, thereby advancing the state of automated vulnerability repair.

### **4. Methodology and Approach**

The paper introduces AGENTICREPAIR, an agentic vulnerability repair framework designed to integrate and leverage multi-faceted program context. The framework operates in two main steps: multi-faceted program context engineering, followed by patch synthesis with the engineered context.

**Formal Definition:**
AGENTICREPAIR is defined as a tuple â¨V, E, A, C, Pâ©, where:
*   **V:** Input vulnerability (description + AddressSanitizer report).
*   **E:** Sandbox environment (project repository R + vulnerability reproduction harness H).
*   **A:** Set of four specialized subagents: {A_struct, A_exec, A_hist, A_repair}.
*   **C:** Unified multi-faceted program context: {C_struct, C_exec, C_hist}.
*   **P:** Candidate patch generated by A_repair.

**A. Multi-Faceted Program Context Engineering (Step 1)**
In this phase, three specialized context engineering subagents operate in parallel within a sandbox environment. Guided by the vulnerability description, each subagent independently extracts relevant information concerning program structure, runtime execution behavior, or commit history. These partial contexts are then synthesized into a unified multi-faceted program context (C).

1.  **Code-Structure Context (C_struct) by A_struct:**
    *   **Task:** Identify the vulnerability type and relevant code locations based on V.
    *   **Process:** Performs semantic code analysis to extract structural information, including data-flow relations, taint propagation paths, control-flow dependencies, and vulnerable memory operation patterns around the identified site.
    *   **Output:** A compact, structured representation summarizing findings, vulnerable location, data-flow summary, structural concerns, and high-level fix suggestions.

2.  **Runtime-Execution Context (C_exec) by A_exec:**
    *   **Task:** Classify vulnerability type and identify relevant code locations using V.
    *   **Process:** Triggers the reproduction harness (H) under dynamic instrumentation to capture precise runtime behaviors. This includes crash signatures (address and type), full stack backtraces, memory access patterns and violations, and anomalous execution states around the vulnerable site.
    *   **Output:** A compact, structured representation of observed runtime outputs and root cause analysis, encompassing the crash location/type, key backtrace frames, memory state observations, runtime vulnerability insights, and high-level fix suggestions.

3.  **Commit-History Context (C_hist) by A_hist:**
    *   **Task:** Identify key files and functions involved in the vulnerability using V.
    *   **Process:** Mines the version-control history preceding the vulnerable commit to reconstruct evolutionary patterns. It extracts relevant commit metadata, code change summaries, and historical modification contexts around the identified sites.
    *   **Output:** A compact, structured representation summarizing historical evidence and root cause analysis, including analyzed files/functions, relevant commits with change summaries and relevance scores, vulnerability origin insights, and high-level fix suggestions.

**B. Patch Synthesis with Engineered Multi-Faceted Program Context (Step 2)**
In this phase, the repair subagent (A_repair) performs context-conditioned patch synthesis.

1.  **Context Embedding:** The unified multi-faceted program context (C) is persistently embedded into an episodic memory (M) accessible to A_repair. This ensures that all repair decisions are grounded in a comprehensive, cross-dimensional understanding of the program.
2.  **Synthesis-Verification Loop:** Guided by V, A_repair iteratively generates minimal candidate patches (P). For each candidate patch:
    *   It applies the patch to the project repository (R).
    *   Rebuilds the project.
    *   Re-executes the reproduction harness (H).
    *   Continuously reflects on verification outcomes within the memory window.
3.  **Patch Output:** The loop continues until the sanitizer reports no violation, at which point the verified patch is considered the final output of AGENTICREPAIR.

**Implementation Details:**
*   **Framework:** AGENTICREPAIR is built atop the `smolagents` library as a custom multi-agent orchestration framework.
*   **Subagents:** Each subagent is implemented as a `ToolCallingAgent` instance, operating via structured JSON tool calls, contrasting with `CodeAgent` which generates free-form Python code.
*   **LLM Backend:** The `gpt-5.2-2025-12-11` model is used for all subagents, configured with its default medium reasoning effort and a fixed temperature of 1.0.
*   **Step Budgets:** Context engineering subagents (A_struct, A_exec, A_hist) are allotted a maximum of 20 steps each. The repair subagent (A_repair) is allowed up to 75 steps to accommodate iterative patch refinement, aligning with SEC-Bench benchmark configurations.
*   **Environment:** The entire pipeline executes within isolated Docker environments to ensure reproducibility.

**Experimental Design:**
*   **Research Questions (RQs):**
    *   **RQ1:** What is the accuracy of AGENTICREPAIR for automated vulnerability repair?
    *   **RQ2:** What are the contributions of the components of AGENTICREPAIR?
*   **Benchmark:** SEC-Bench, a benchmark comprising 300 real-world C/C++ vulnerable instances (200 CVE-sourced, 100 OSS-Fuzz cases). Each instance includes a full codebase, build environment, reproduction harness, human-readable Proof-of-Concept (PoC), and sanitizer-based verification.
*   **Baselines:** Four LLM-based agentic frameworks: OpenHands, SWE-Agent, Aider (all using Claude 3.7 Sonnet), and Smolagents (with GPT-5.2, GPT-5-mini, and GPT-5-nano as base models).
*   **Evaluation Metric:** Success rate, defined as the number of successfully repaired instances divided by the total. A repair is considered successful if the patched code compiles, prevents the original PoC from triggering the sanitizer error, and introduces no new sanitizer-detectable issues.
*   **Ablation Study:** To address RQ2, AGENTICREPAIR is compared against variants:
    *   Without individual context facets (w/o Code-Structure, w/o Program-Execution, w/o Commit-History).
    *   With a single-agent scaffold.
    *   With smaller base models (GPT-5-Mini, GPT-5-Nano).
    *   Evaluation is conducted using three success criteria: generous, medium, and strict, which differ in how they interpret the program's exit code post-patch.

### **5. Main Findings and Results**

The experimental evaluation of AGENTICREPAIR on the SEC-Bench benchmark provided insights into its performance and the contributions of its constituent components.

**RQ1: Accuracy of AGENTICREPAIR for Automated Vulnerability Repair**
AGENTICREPAIR demonstrated a notable performance improvement in automated vulnerability repair:
*   **Overall Success Rate:** AGENTICREPAIR achieved a 73% success rate, successfully repairing 220 out of 300 real-world vulnerable instances on the full SEC-Bench dataset. This result represents a 29% absolute improvement over the strongest baseline (Smolagents with GPT-5.2), which achieved a 44.7% success rate.
*   **CVE-Sourced Vulnerabilities:** For the 200 CVE-sourced instances, AGENTICREPAIR achieved a 75% success rate (150/200). This substantially surpassed state-of-the-art agentic frameworks like OpenHands (34%), SWE-Agent (31.5%), and Aider (23.5%) by margins of 41-52%. It also outperformed Smolagents with GPT-5.2 (45%) by 30%.
*   **OSS-Fuzz Vulnerabilities:** On the 100 OSS-Fuzz instances, AGENTICREPAIR achieved a 70% success rate (70/100), repairing 26 more vulnerabilities than the strongest Smolagents baseline.
*   **Complex Vulnerabilities:** The framework demonstrated an ability to handle complex, cross-file security issues, with 40% (90/220) of successful repairs involving edits across multiple files.
*   **Case Study:** The paper highlighted a case study (php.ossfuzz-42501106), a heap-use-after-free vulnerability. AGENTICREPAIR, guided by the multi-faceted context, diagnosed an ownership mismatch and generated a patch that updated construction sites to use `zend_string_copy()` before `zend_free_trampoline()`, fixing the lifetime invariant.

These results indicate that by integrating a unified multi-faceted program context (program structure, runtime execution behavior, and commit history), AGENTICREPAIR can significantly improve vulnerability repair success rates compared to existing agentic approaches that primarily rely on basic tool execution and LLM reasoning.

**RQ2: Contributions of AGENTICREPAIR Components (Ablation Study)**
The ablation study, conducted on 200 CVE instances, analyzed the impact of AGENTICREPAIR's key components:
*   **Multi-Faceted Program Context:** Removing any single context facet (code-structure, runtime-execution, or commit-history) resulted in small performance degradations in strict mode: -1.5% without code-structure, -0.5% without program-execution, and -2.0% without commit-history. This suggests that the three context types are complementary and collectively contribute to the framework's robustness rather than any single context being solely responsible for performance.
*   **Multi-Agent Scaffolding:** Replacing the multi-agent scaffold with a single-agent setup led to a substantial decline of 44.5% in success rate (from 75% to 30.5%). This finding indicates that the multi-agent architecture effectively distributes the cognitive load and enables more reliable utilization of the engineered insights compared to a monolithic agent.
*   **Base Model Capacity:** Reducing the capacity of the base LLM had a significant impact. Replacing GPT-5.2 with GPT-5-Mini decreased performance by 25% (from 75% to 50%), and using GPT-5-Nano resulted in a 65% reduction (to 10%). This demonstrates that sufficiently capable base models are essential for interpreting the provided insights and synthesizing correct patches, even with the engineered context and multi-agent structure.

Collectively, the ablation study indicates that AGENTICREPAIR's performance arises from the synergistic effect of its multi-faceted program context, the multi-agent scaffolding, and the use of a capable base model.

**Additional Discussion Points:**
*   **Patch Similarity to Reference Repairs:** AGENTICREPAIR rarely reproduced the exact reference patches. None of the 298 generated patches exactly matched the gold patches. The average normalized patch-line Jaccard similarity was low (0.1177), and content-only similarity was even lower (0.0561). However, the average file-level Jaccard similarity was higher (0.5836), suggesting that the generated repairs often targeted the correct files or regions but introduced semantically equivalent, novel edits.
*   **Failure Analysis:** Out of 80 failures, the dominant type was "Improper Format" (IF, 53 cases or 66.2%), where the agent produced a patch in an invalid or non-applicable format. "Still Vulnerable" (SV) accounted for 25 cases (31.2%). Few "No Patch" (NP, 2 cases) or "Compilation Error" (CE, 0 cases) failures were observed. Successful patches tended to be narrower (median 32 edited lines, 1 file) compared to failed patches (median 47.5 edited lines, 2 files), with failed patches often being excessively broad or unstable. Dynamic runtime attribution indicated that 53 failures were due to syntactically invalid or truncated diffs during patch application, and 22 were due to misalignment between the sanitizer-oriented repair objective and broader PoC harness acceptance conditions.
*   **Subagent Trajectory Patterns:** Analysis of tool-calling trajectories revealed early role specialization among context engineering subagents (e.g., CodeQL for A_struct, GDB/Valgrind for A_exec, PyDriller for A_hist), followed by a shift towards command-line tools for repository inspection. The repair subagent (A_repair) utilized the most interaction turns (averaging 28 steps compared to 7-9 for upstream agents), predominantly using command-line tools, suggesting that the primary challenge lies in integrating, testing, and refining signals within the final repair loop.
*   **Performance Across Projects and Vulnerability Categories:** AGENTICREPAIR showed varied success across projects, with high rates on ImageMagick (90.3%), LibreDWG (85%), mruby (80%), and GPAC (76.7%), but lower on projects like exiv2 (20%). The low performance on exiv2 was attributed to broad, malformed patches that failed at the `git apply` step. Across vulnerability categories, the framework was broadly effective for buffer overflow/out-of-bounds (74.7%) and null dereference (73.1%) vulnerabilities. However, complex object lifetime and deallocation semantics, such as use-after-free (68.6%) and invalid/double-free cases (33.3%), presented greater challenges.

### **6. Significance and Potential Impact**

The research presented in this paper, with AGENTICREPAIR, introduces a design direction for automated vulnerability repair that demonstrates notable significance and potential impact:

*   **Advancement in Automated Vulnerability Repair:** AGENTICREPAIR is presented as the first agentic framework that explicitly integrates multi-faceted program context engineering for automated vulnerability repair. By operationalizing the assembly of code-structure, runtime-execution, and commit-history contextsâwhich are routinely utilized by human security engineersâit addresses a critical limitation in existing agentic AI approaches that were primarily designed for general program repair.
*   **Enhanced Performance and Robustness:** The substantial performance increase, achieving a 73% success rate on the SEC-Bench benchmark and outperforming the strongest baselines by 29%, suggests a significant step forward in the efficacy of automated vulnerability patching. The ability to repair complex, multi-file vulnerabilities (40% of successful cases) indicates an improved capacity to handle real-world scenarios.
*   **Validation of Context Engineering:** The ablation study confirms that the identified context facets are not only individually helpful but also mutually complementary. This establishes multi-faceted program context engineering as a key design principle. It bridges the gap between the diagnostic processes of human security engineers and the operational capabilities of AI agents, providing a structured approach for AI to build comprehensive program understanding.
*   **Insights into Agentic System Design:** The findings on multi-agent scaffolding and base model capacity provide valuable insights for the broader development of agentic systems. The significant performance drop with a single-agent setup underscores the importance of distributing cognitive load through specialized subagents. Concurrently, the necessity of highly capable base models highlights the need for continued advancements in LLM reasoning capabilities to effectively interpret and leverage engineered context.
*   **Reduced Vulnerability Exposure:** By enabling more effective and automated patching, AGENTICREPAIR has the potential to substantially reduce the time and effort required to fix security flaws. This could lead to a decrease in the median time from vulnerability disclosure to patch deployment, thereby shortening vulnerability exposure windows and mitigating the risk of security incidents in real-world software systems.
*   **Direction for Future Research:** The failure analysis provides actionable insights for future work, such as incorporating lightweight patch integrity checks and extending verification to include functional correctness and resource constraints alongside sanitizer outcomes. These directions could address a significant portion of current failures (estimated 93.8%), further improving the framework's reliability and performance.
*   **Reproducibility and Transparency:** The commitment to releasing all experimental artifacts, including full execution logs, trajectories, and a ready-to-run implementation, enhances research transparency and facilitates further independent research and validation in the community.

In conclusion, AGENTICREPAIR represents a notable contribution to the field of automated software security, demonstrating that deliberate and multi-faceted program context engineering is a critical factor in developing more effective and intelligent agentic systems for complex security challenges.
