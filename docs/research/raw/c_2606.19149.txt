## Research Paper Report: OpenAnt: LLM-Powered Vulnerability Discovery Through Code Decomposition, Adversarial Verification, and Dynamic Testing

### 1. Authors and Institution(s)

The research paper "OpenAnt: LLM-Powered Vulnerability Discovery Through Code Decomposition, Adversarial Verification, and Dynamic Testing" was authored by Nahum Korda and Gadi Evron. Both authors are affiliated with Knostic.ai, as indicated by their provided email addresses (nahum.korda@knostic.ai and gadi@knostic.ai).

### 2. How This Work Fits into the Broader Research Landscape

The field of automated vulnerability discovery in large codebases has traditionally faced significant challenges. Static Application Security Testing (SAST) tools, while widely deployed for over two decades, often yield high false-positive rates, ranging from low single-digit percentages to over 40% in empirical studies. This warning noise contributes to developer distrust, alert fatigue, and limits their effective adoption. Furthermore, SAST tools are constrained by their reliance on manually engineered, rule-based patterns, which may miss vulnerabilities not covered by predefined rules or inaccurately flag benign code.

Dynamic approaches, such as fuzzing, offer an alternative by executing programs with generated inputs to uncover bugs. However, fuzzing typically demands substantial infrastructure, compilation, and instrumentation specific to each target, often focusing on narrow classes of vulnerabilities like memory safety issues.

Recent advancements in Large Language Models (LLMs) have introduced new capabilities for semantic reasoning and code understanding, suggesting a potential to overcome some limitations of traditional static analysis. LLMs can analyze program syntax and semantics, infer developer intent, and perform various automated code analysis tasks. However, applying LLMs to repository-scale security analysis presents its own set of technical challenges. These include managing context effectively, as model accuracy can degrade with long inputs ("lost-in-the-middle" effect), computational cost associated with extensive code analysis, and the risk of generating incorrect conclusions from incomplete program context. Additionally, evaluating LLM-based systems reliably is complicated by issues such as benchmark contamination (where training data leaks into evaluation benchmarks), data quality problems in existing vulnerability datasets, and the potential for "shortcut learning" in synthetic benchmarks.

OpenAnt positions itself within this landscape by integrating static program analysis with LLM-based reasoning in a multi-stage pipeline, aiming to mitigate the limitations of both traditional SAST and existing LLM-only approaches. It builds upon prior work in pattern-based SAST, LLM-assisted code security analysis (such as Google's "Big Sleep" and industrial systems like Claude Code Security), LLM-based autonomous penetration testing, fuzzing, and automated exploit generation. Unlike traditional SAST, OpenAnt focuses on semantic reasoning and explicit exploitability verification. It extends LLM-assisted analysis by introducing a closed-loop verification architecture that moves beyond static reasoning to include adversarial attacker simulation and automated exploit generation, thereby addressing the challenge of distinguishing theoretical vulnerabilities from practically exploitable ones. While drawing inspiration from autonomous penetration testing agents, OpenAnt performs its reasoning directly on source code, enabling pre-deployment analysis. Its dynamic verification complements fuzzing by generating targeted exploit scenarios from semantic analysis, rather than exploring vast input spaces. The system's emphasis on ephemeral, automatically generated exploit environments also relates to automated exploit generation research but applied at the source code level.

By combining these disparate elements, OpenAnt seeks to provide a practical and scalable path toward automated security analysis that can identify real-world vulnerabilities with reduced false positives and concrete evidence of exploitability.

### 3. Key Objectives and Motivation

The primary motivation for developing OpenAnt stems from the recognized deficiencies in existing automated vulnerability discovery methods. Traditional SAST tools, despite their widespread use, struggle with high rates of false positives, which lead to developer alert fatigue and a lack of trust in reported findings. Their rule-based nature also limits their ability to detect novel or complex vulnerabilities that do not conform to predefined patterns. Conversely, while large language models demonstrate advanced capabilities in understanding code semantics, their direct application to large codebases for security analysis introduces issues of context management, computational cost, and the difficulty of verifying LLM-generated vulnerability hypotheses. There is a need for a system that can leverage the semantic reasoning power of LLMs while addressing these practical constraints and providing reliable, actionable security insights.

Against this background, OpenAnt was designed with several key objectives:

*   **To integrate static program analysis with LLM-based reasoning:** The system aims to combine the efficiency of static analysis for large-scale code processing with the nuanced semantic understanding offered by LLMs.
*   **To significantly reduce the analysis surface for LLMs:** By filtering out irrelevant code and focusing on externally reachable components, OpenAnt seeks to manage the computational cost and context limitations inherent in LLM processing of large repositories.
*   **To introduce a robust, multi-stage verification methodology:** A core objective is to evaluate candidate vulnerabilities not just for their theoretical presence but also for their practical exploitability through adversarial attacker simulation and dynamic testing. This aims to substantially reduce false positives compared to traditional static analysis.
*   **To generate concrete evidence of exploitability:** By automatically constructing and executing exploit environments, the system aims to move beyond merely flagging suspicious patterns to providing reproducible proof of concept.
*   **To maintain manageable analysis costs:** Through strategic filtering and a phased approach, OpenAnt seeks to make repository-scale LLM-based security analysis economically feasible.
*   **To identify previously unknown vulnerabilities in real-world software:** The ultimate objective is to apply the system to actively maintained, complex open-source projects and demonstrate its capability to discover actual security flaws that have not been publicly reported.

These objectives collectively aim to create a practical, scalable, and reliable automated vulnerability discovery system that bridges the gap between the limitations of current tools and the potential of advanced AI reasoning.

### 4. Methodology and Approach

OpenAnt employs a six-stage, multi-pipeline architecture designed to progressively narrow the analysis scope while increasing the depth of verification for potential vulnerabilities. The pipeline integrates traditional static program analysis with LLM-based reasoning and dynamic exploit validation.

**Stage 1: Code Parsing**
The initial stage involves parsing the target source code repository. This process utilizes language-specific Abstract Syntax Tree (AST) analysis to extract all functions, recording their signatures, bodies, source file locations, and inter-function call relationships. A bidirectional call graph is constructed from these relationships, linking callers and callees across different files. OpenAnt supports multiple programming languages, including Python, JavaScript/TypeScript, Go, C/C++, Ruby, and PHP, using either native AST libraries or tree-sitter grammars to produce a unified intermediate representation.

**Stage 2: Unit Generation and Reachability Filtering**
Parsed functions are transformed into self-contained "analysis units." Each unit comprises the primary target function, its resolved dependencies (transitively inlined up to a default depth of three levels), and metadata indicating whether the function is reachable from external inputs.
A crucial step in this stage is **reachability filtering**. OpenAnt identifies "entry points"âfunctions that directly accept externally supplied input (e.g., HTTP handlers, command-line argument processors, WebSocket handlers). A breadth-first traversal of the call graph is performed starting from these entry points to identify all reachable functions. Only these externally reachable functions are retained as analysis units for subsequent LLM-based stages, significantly reducing the analysis surface. For instance, this stage achieved a 97% reduction in analysis units for OpenSSL and 94.6% for Grafana.

**Stage 3: Exposure Classification**
In this stage, an LLM agent (Claude Sonnet) analyzes each reachable unit. The agent performs tool-assisted navigation, which includes searching for callers, inspecting function implementations, and tracing call paths within the codebase. The purpose is to classify the unit's security exposure into one of four categories: "Exploitable" (vulnerable code reachable from external input), "Vulnerable-internal" (potentially unsafe code not reachable from user input), "Security control" (defensive logic), or "Neutral" (no apparent security relevance). Only units classified as "Exploitable" proceed to the next stage, further narrowing the focus. In the OpenSSL example, this stage resulted in an additional 87% reduction of units.

**Stage 4: Vulnerability Detection**
Units identified as "Exploitable" undergo detailed vulnerability detection by a different LLM (Claude Opus). This stage utilizes a language-agnostic prompt that instructs the model to answer three questions: "What does this code do?", "Where does the input originate?", and "What security risk may arise from this behavior?". The LLM then produces a structured assessment, classifying the unit as "vulnerable," "bypassable," "inconclusive," "protected," or "safe." The language-agnostic nature of the prompt aims to enable generalizable semantic security reasoning across diverse programming languages.

**Stage 5: Adversarial Verification**
All units that received any finding in Stage 4 (including "safe" or "protected" assessments) are subjected to adversarial verification. In this stage, the LLM (Claude Opus) simulates a remote attacker operating under predefined realistic constraints, such as browser-based interaction only, no server-side access, no administrative credentials, and no ability to modify server files. The model attempts to construct concrete exploitation paths, tracing steps, and identifying conditions that prevent or enable exploitation. A key design choice involves requiring the model to explore multiple exploitation approaches. The verification process also incorporates a "victim requirement," ensuring that valid vulnerabilities must affect a party other than the attacker, thus excluding self-impact scenarios. The output is a structured document detailing the function, each exploitation attempt's outcome, and a final assessment.

**Stage 6: Dynamic Verification**
Findings that remain plausible after adversarial verification are submitted for dynamic testing via automated exploit generation. Another LLM (Claude Sonnet) is tasked with generating the necessary components for a proof-of-concept exploit: a Dockerfile for the execution environment, a test script to reproduce the exploit, a requirements file for dependencies, and optionally, a Docker Compose configuration for multi-service scenarios. This generated exploit environment is then executed within an isolated Docker container, subject to resource limits (e.g., read-only filesystem, 512 MB memory, single CPU, no privilege escalation, 120-second timeout). The container's output is a JSON object classifying the result as CONFIRMED, NOT_REPRODUCED, BLOCKED, INCONCLUSIVE, or ERROR. If an ERROR occurs, the LLM receives feedback and attempts to generate a corrected test environment for up to three iterations. All generated artifacts are ephemeral and discarded after execution, ensuring that concrete evidence of exploitability is produced without relying on persistent exploit templates.

**Evaluation Methodology**
OpenAnt's evaluation strategy avoids standard security benchmarks (like Juliet Test Suite or OWASP Benchmark) due to concerns about benchmark contamination, data quality issues, and shortcut learning with LLM-based systems. Instead, the evaluation focuses on **real-world vulnerability discovery** in actively maintained open-source projects. This approach aims to provide direct evidence of the system's ability to identify previously unknown vulnerabilities under realistic conditions. The scope of detection is specifically focused on vulnerabilities arising from unsafe propagation of externally controlled input to security-sensitive operations, such as injection attacks, path traversal, SSRF, authorization bypass, and XSS.

### 5. Main Findings and Results

OpenAnt was evaluated on eight real-world open-source projects spanning six programming languages (C, JavaScript, TypeScript, PHP, Go, Python, Ruby), comprising a total of 64,132 functions. The evaluation measured the system's scalability, detection capability, false-positive mitigation, and practical exploitability.

**Scalable Repository Analysis:**
The pipeline demonstrated significant reduction in the analysis surface.
*   **Static filtering (Stage 2):** From 64,132 initial functions, reachability filtering reduced the set to 2,281 reachable units, representing a 96.4% reduction, before any LLM processing.
*   **Exposure classification (Stage 3):** This stage further refined the set to 586 externally exploitable units, which is less than 1% of the original codebase.
*   For example, in OpenSSL, 15,232 functions were reduced to 390 reachable units (97.4% reduction), and then to 49 externally exposed units (99.7% reduction from original). Ultimately, only 0.02% of original functions produced confirmed findings in OpenSSL.

**Practical Vulnerability Discovery:**
*   **Confirmed Findings:** After adversarial verification (Stage 5), OpenAnt identified 190 vulnerability candidates across the evaluated repositories.
*   **Diversity of Findings:** These findings spanned over 30 distinct vulnerability classes, including Authorization Bypass (IDOR/Missing Authorization, Unauthenticated Endpoint/Auth Bypass), Mass Assignment/Privilege Escalation, Server-Side Request Forgery (SSRF), Path Traversal/File Read/Zip Slip, Cross-Site Scripting (XSS)/Content Injection, SQL/NoSQL Injection, Resource Exhaustion/DoS, and Header Injection.
*   **Generalizability:** The detection prompt remained language-agnostic across all six programming languages, indicating that the semantic vulnerability reasoning based on input tracing and attacker capabilities generalizes across different programming ecosystems.
*   **Vulnerability Density:** Workflow automation platforms (Flowise, n8n) exhibited the highest density of confirmed vulnerabilities, reflecting their complexity in handling user-defined workflows and external service interactions. Conversely, mature frameworks (Rails) and cryptographic libraries (OpenSSL) showed fewer findings.

**Exploit Reproducibility (Dynamic Verification):**
*   **Confirmation Rate:** Of the 190 vulnerability candidates confirmed by adversarial verification, 144 (75.8%) were successfully reproduced through automated dynamic exploit generation (Stage 6) in sandboxed containers.
*   **Outcomes:** The dynamic verification outcomes were: CONFIRMED (75.8%), INCONCLUSIVE (12.6%), NOT_REPRODUCED (6.8%), ERROR (4.2%), and BLOCKED (0.5%).
*   **Vulnerability Type Specificity:** Vulnerability classes requiring direct input manipulation, such as Command Injection (100% confirmation rate), Path Traversal (88.9%), Authentication Bypass (83.3%), and Mass Assignment (76.9%), showed the highest dynamic confirmation rates. Issues dependent on complex timing or environment were more challenging to reproduce automatically.

**False Positive Mitigation:**
Adversarial verification (Stage 5) served as a primary mechanism for reducing false positives.
*   **Elimination Rate:** Of 376 findings flagged in Stage 4, 190 were confirmed after attacker simulation, representing a 49.5% elimination rate of findings initially identified as potentially vulnerable.
*   **Common Rejection Causes:** Common reasons for rejection included effective input sanitization, authentication barriers, findings that only affected the attacker's own data (violating the victim requirement), and platform-level protections.

**Cost Efficiency Through Staged Filtering:**
*   **Total Cost:** The total cost for evaluating all eight repositories was $1,461.25.
*   **Cost Distribution:** Exposure classification (Stage 3) accounted for the majority of the cost (72.9%) due to the agentic code exploration required.
*   **Impact of Filtering:** The static reachability filtering (Stage 2) significantly impacted cost efficiency. Without this stage, the estimated cost for analyzing all extracted functions would have been approximately $23,700. This indicates that the pipeline's static filtering stages reduced the total analysis cost by more than 96%, making repository-scale LLM-based analysis economically feasible.

These results collectively indicate that OpenAnt's closed-loop pipeline can identify exploitable vulnerabilities in real-world code, effectively mitigate false positives, and do so at a manageable cost by strategically integrating static analysis with LLM-powered reasoning and dynamic validation.

### 6. Significance and Potential Impact

OpenAnt presents a significant contribution to the field of automated software security analysis by addressing critical limitations inherent in existing methodologies. Its primary significance lies in the development of a **closed-loop vulnerability discovery pipeline** that integrates semantic reasoning with concrete exploit validation. This contrasts with traditional SAST tools that often report theoretical weaknesses with high false-positive rates, and with earlier LLM-based approaches that primarily relied on static reasoning without robust, automated verification.

The potential impact of OpenAnt is multi-faceted:

*   **Reduced False Positives and Enhanced Trust:** By incorporating adversarial verification and dynamic exploit generation, OpenAnt shifts the objective from merely identifying suspicious code patterns to producing concrete, reproducible evidence of exploitability. This approach substantially reduces the number of false positives, which has historically been a major barrier to the adoption and effectiveness of static analysis tools. Higher precision can lead to increased developer trust and more efficient vulnerability remediation workflows.
*   **Actionable Security Findings:** The dynamic verification stage provides executable exploit environments, offering developers and security teams immediate, actionable proof-of-concept for identified vulnerabilities. This eliminates the need for manual reproduction of findings, accelerating the triage and patching process.
*   **Scalable and Cost-Efficient LLM-based Analysis:** OpenAnt demonstrates a practical method for applying sophisticated LLM capabilities to large, real-world codebases. The multi-stage filtering pipeline, particularly static reachability filtering, dramatically reduces the volume of code processed by LLMs. This intelligent pre-filtering makes repository-scale LLM analysis economically feasible, overcoming a major challenge related to the computational cost and context limitations of large language models.
*   **Generalizable Vulnerability Detection:** The use of language-agnostic prompts and semantic reasoning about input origins and sensitive operations allows OpenAnt to detect diverse vulnerability types across multiple programming languages and application architectures. This generalizability reduces the need for language-specific rule engineering or prompt customization, potentially enabling broader applicability.
*   **Discovery of Previously Unknown Vulnerabilities:** The evaluation on actively maintained, real-world open-source projects demonstrated OpenAnt's capacity to identify previously unreported security flaws. This indicates its potential to augment existing security testing efforts by discovering vulnerabilities that might evade conventional tools.
*   **Advancement of LLM Application in Security:** OpenAnt contributes to the understanding of how LLMs can be effectively harnessed for complex security tasks. By integrating agentic code exploration and attacker simulation, it pushes the boundaries of LLM-powered reasoning in a practical security context.
*   **Open-Source Contribution:** The release of OpenAnt under the Apache 2.0 license fosters community involvement, transparency, and further research and development in automated vulnerability discovery, potentially accelerating innovation in this domain.

In summary, OpenAnt offers a viable path toward scalable and reliable automated security analysis by strategically combining the strengths of static analysis, advanced LLM reasoning, and rigorous exploit validation. Its methodological contributions and demonstrated capabilities could enhance the efficiency and effectiveness of vulnerability discovery processes across the software industry.
